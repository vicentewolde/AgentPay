# Evidencia · T31 — `policy_rail` paga una factura x402 real

Fecha: 2026-09-04

Todo lo de acá corrió contra Stellar testnet real y el bazaar real
(`stellar-bazaar-x402.vercel.app`), con el facilitator de OpenZeppelin en el
medio. Nada está simulado ni mockeado.

## 1. El hueco que la lectura de código de T22 no había visto

`M-12` (T22) concluyó, leyendo `@x402/stellar`, el facilitator y el SDK, que
nada en la cadena de pago restringe el tipo de dirección del pagador. Eso sigue
siendo cierto. Lo que faltaba mirar era el **paso de firma**, siguiendo la
cadena de llamadas del SDK instalado:

```
ExactStellarScheme.createPaymentPayload
  └── tx.signAuthEntries({ address, signAuthEntry, expiration })   (SDK contract/)
        └── callback interno:  return base64ToUint8Array(signedAuthEntry)   ← bytes crudos, siempre
              └── authorizeEntry(entry, callback, …)               (SDK base/auth.js)
                    └── rama "firma pelada":
                        publicKey = Address.fromScAddress(addrAuth.address).toString()
                        Keypair.fromPublicKey(publicKey)           ← revienta con un "C…"
```

`@stellar/stellar-sdk@17.0.1`, `lib/esm/base/auth.js`:

```js
} else if (isUint8Array(sigResult)) {
  signature = sigResult;
  publicKey = Address.fromScAddress(addrAuth.address).toString();
}
...
if (!Keypair.fromPublicKey(publicKey).verify(payload, signature)) {
  throw new Error(`signature doesn't match payload`);
}
```

Un contract id no es una llave Ed25519, así que ese `Keypair.fromPublicKey`
falla antes de verificar nada. El camino estándar del cliente x402 es, en la
práctica, solo para cuentas clásicas. Detalle y salida elegida en
`DECISIONES.md` → `V-12`.

## 2. Los dos rechazos reales del facilitator, en orden

Ninguno de los dos aparece en los tipos ni en la documentación: salieron de
pagar de verdad y leer el cuerpo del `402` de vuelta.

**Primero:**

```json
{"ok":false,"error":{"code":"invalid_exact_stellar_payload_malformed","message":"Pago inválido.","retryable":false,"stage":"payment"}}
```

Causa: el SDK 17 arma `sorobanCredentialsAddressV2` (CAP-71) y el facilitator
viaja con el SDK 16, que no lo decodifica. Verificado leyendo el tipo de
credencial de la transacción que producíamos:

```
credentials type: sorobanCredentialsAddressV2     ← rechazada
credentials type: sorobanCredentialsAddress       ← con useUpgradedAuth: false
```

Ver `V-14`.

**Segundo, ya con la transacción parseable:**

```json
{"ok":false,"error":{"code":"invalid_exact_stellar_payload_event_not_transfer","message":"Pago inválido.","retryable":false,"stage":"payment"}}
```

Causa: `validateSimulationEvents` (facilitator) exige que **todo** evento de
contrato de la simulación sea un `transfer`:

```js
const symbol = topics[0].sym().toString();
if (symbol !== "transfer") {
  return invalidVerifyResponse("invalid_exact_stellar_payload_event_not_transfer", fromAddress);
}
```

El evento de auditoría de `policy_rail` (`("policy_rail", "authorised", day)`)
cae exactamente ahí. Ver `V-13` — y cómo se decidió quitarlo, con la
confirmación explícita del usuario, no en silencio.

Los cinco tests nuevos cubren lo único de este hito que se puede probar sin
