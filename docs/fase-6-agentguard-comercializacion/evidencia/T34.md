## Verificación en vivo — simulación de una firma real de Freighter contra el servidor real

Se generó un keypair de prueba (testnet, sin fondos reales) y se firmó el
challenge exactamente como lo haría la extensión Freighter (SEP-0053:
`sha256("Stellar Signed Message:\n" + mensaje)`, firma Ed25519 cruda sobre
ese hash), sin usar ningún atajo del servidor.

### 1. Pedir un challenge

```json
{"ok":true,"nonce":"1be35ca6-f5ff-4b56-9438-c66e66811bd9","message":"TirevPay quiere confirmar que controlás esta wallet.\nNonce: 1be35ca6-f5ff-4b56-9438-c66e66811bd9"}
```

### 2. Verificar la firma real

```json
{"ok":true,"address":"GAAAOQLDFBCIT3ZPDPOEN6J3QBNBFBMCUDZPGDIIU4PVM7XPT437UJAR"}
```

Cookie resultante: `agentpay_sid=04406fec-13b3-b4e7-f3a7-76271b9ddabb`.

### 3. Iniciar sesión con esa cookie — el servidor devuelve la wallet conectada

```json
{
  "ok": true,
  "credentialHash": "6cc883b6f18cb892ffab47312a2c8bac4cdb82625b4f2a2b5346371ea5856a52",
  "mandateHash": "89ad8b8a57ffabe719e00fd27471573ff3277dd84842447e709ecd2ed7a7687f",
  "agentStatus": "Active",
  "walletAddress": "GAAAOQLDFBCIT3ZPDPOEN6J3QBNBFBMCUDZPGDIIU4PVM7XPT437UJAR"
}
```

### 4. La MISMA wallet, un challenge nuevo, una verificación nueva → la MISMA cookie

```
--- primera cookie ---
agentpay_sid  04406fec-13b3-b4e7-f3a7-76271b9ddabb
--- segunda cookie (mismo wallet, sesión nueva) ---
agentpay_sid  04406fec-13b3-b4e7-f3a7-76271b9ddabb
```

Confirma la derivación determinística (`C-9`): la misma wallet siempre cae
en el mismo `tenant_id`, sin necesidad de guardar ese mapeo en ningún lado.

### 5. Casos de seguridad — los dos rechazados correctamente

Reintentar el mismo nonce ya usado:

```json
{"ok":false,"code":"InvalidArguments","message":"falta address, nonce o signature, o el nonce ya se usó"}
```

Firma de una wallet distinta a la que dice ser:

```json
{"ok":false,"code":"InvalidSignature","message":"la firma no corresponde a esa wallet"}
```

## Un bug real, encontrado en el navegador, no leyendo documentación

El primer intento llamaba a `freighterApi.requestAccess()` directo. Contra
un navegador **sin la extensión Freighter instalada**, esa llamada nunca
resuelve ni rechaza — el botón queda colgado para siempre, sin ningún
mensaje de error. Encontrado clickeando el botón real en el Browser pane
(sin la extensión) y viendo que no pasaba nada. Corregido llamando primero
a `freighterApi.isConnected()`, que sí responde rápido en los dos casos —
verificado con un timeout explícito de 3-4s antes y después del fix.
