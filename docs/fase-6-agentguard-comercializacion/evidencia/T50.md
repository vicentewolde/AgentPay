# T50 — guía de integración de CloudOps

## Alcance

Se agregó [`examples/cloudops-partner-integration.md`](../../../examples/cloudops-partner-integration.md), una guía reproducible para que un partner ficticio, CloudOps, integre la Partner API de AgentPay sin modificar el repositorio. Incluye comandos `curl` completos para recibir una key por el flujo operador `pnpm run partner:create`, crear un tenant, consultar agentes, abrir un `consent_session` con un grant que restringe `payTo`, entregar la URL al principal y consultar tanto la sesión como el mandato resultante.

La guía no agrega rutas HTTP, no toca paquetes, aplicaciones ni contratos, y no cambia ningún criterio de autorización. Aclara que la key se emite una sola vez, que `consent_url` es la única URL que se entrega al principal, que el principal revisa el grant y firma con Freighter, y que CloudOps no firma ni custodia wallets.

## Contrato verificado al redactar

- `POST /v1/tenants` y `POST /v1/consent_sessions` exigen `Idempotency-Key`; la guía conserva la misma key y el mismo cuerpo en reintentos de red o 5xx.
- La sesión muestra `consent_url` mientras está `pending`; tras completarse devuelve `mandate_id` y oculta la URL. Su ventana de firma es una hora, independiente del `valid_until` del mandato.
- El grant de ejemplo cumple el esquema real: `actions` no vacío, `venues`, `assets`, `limits` y `payTo` con una cuenta Stellar testnet válida.
- Se documentaron todos los códigos relevantes de la capa `/v1` y del flujo público del consentimiento, incluido que `ConsentSessionExpired` es un `410` al iniciar/firmar pero un estado `expired` al consultar la sesión.

## Verificación contra servicios reales

Se copió temporalmente una `.env.local` real al worktree aislado (sin
mostrarla ni versionarla), se levantó `pnpm run web` en
`http://127.0.0.1:3400` y se copiaron los comandos de la guía. La pasada creó
un partner `T50 CloudOps` temporal con `pnpm run partner:create`, un tenant,
una sesión con el grant exacto de la guía —incluido `payTo`— y la URL
`/consent/{id}`. El tenant respondió `active`, la lista de agentes fue vacía
antes de la firma y la sesión respondió `pending`, `mandate_id: null` y la
URL esperada.

Un simulador descartable, nunca agregado al repo, generó y fondeó una wallet
testnet, firmó los dos mensajes con `signStellarMessage` de
`@agentpass/core`, firmó la transacción XDR y la envió al endpoint de
anclaje. Terminó en el Mandato
`mdt_01M28BP9HY51F6N1GW1Q0AGA4A` y la transacción Stellar testnet
`34276de2b712957d81000dd5bc87419abb6dda91d9b4f72291ef96f3598029a9`.

También se verificaron el replay con la misma `Idempotency-Key` y el conflicto
por cambiar el cuerpo bajo esa key (`409`/`IdempotencyKeyConflict`). Las
pruebas offline pasaron: sintaxis de todos los bloques `sh`, JSON del grant,
`pnpm typecheck`, `pnpm build` y `pnpm test` (882 pruebas).

Tras cada intento se borraron de Postgres el partner de prueba, API key,
idempotencias, tenant, sesiones, mandato, credencial, agente, bindings y
principal, respetando el orden de claves foráneas de
`packages/directory/src/directory.integration.test.ts`. La `.env.local`
copiada y los simuladores descartables se eliminan antes de abrir el PR.
