## 2. Dónde vive la autoridad

**No en este código.** El contrato del registry rechaza una transacción de
revocación que no venga firmada por la dirección que ancló el Mandato.
`apps/web/src/revocation.ts` agrega un **rechazo mejor**, no la autoridad:
comprueba la wallet contra el principal guardado antes de preparar nada, así
alguien en la cuenta equivocada lee una frase en castellano en vez de un error
de Soroban.

Catorce pruebas, sin HTTP ni red:

```
readPublicView
  ✓ says only whether it is live and until when — never the limits
  ✓ reports revoked and expired distinctly
  ✓ refuses an id that names nothing
proveOwnership
  ✓ accepts the wallet that signed the mandate
  ✓ refuses a different wallet, even with a perfectly valid signature
  ✓ refuses a wallet the system has never seen, with the same refusal
  ✓ refuses a signature that does not match the address
  ✓ refuses a challenge that was already used or expired
  ✓ consumes the challenge before checking the signature
toPrivateView
  ✓ shows the grant only on this side of the proof
  ✓ does not fall over on a document shaped differently than expected
requireRevocable
  ✓ allows an active mandate
  ✓ refuses one that was already revoked, and says with which transaction
  ✓ refuses one that already expired, rather than asking for a pointless signature
```

Tres que valen más que las otras:

- **`says only whether it is live and until when — never the limits`**: un id
  de Mandato se comparte con el partner, así que es un secreto más débil que un
  id de consent session. La prueba comprueba que el JSON público no contiene ni
  `0.30` ni `signaldesk`.
- **`refuses a wallet the system has never seen, with the same refusal`**: mismo
  código que la wallet equivocada, a propósito. Distinguirlas le diría a un
  extraño si una dirección es conocida por el sistema.
- **`consumes the challenge before checking the signature`**: un desafío que
  sobreviviera a un chequeo fallido podría reusarse contra otro Mandato.

## 3. Las tres rutas

| | |
|---|---|
| `GET /api/revoke/{id}` | Estado y vencimiento. Nada más, antes de la prueba |
| `POST /api/revoke/{id}/prepare` | Prueba de wallet **y** preparación de la transacción, en una sola llamada |
| `POST /api/revoke/{id}/submit` | Envía la transacción firmada y espeja la revocación en el directorio |

Prueba y preparación van juntas para que no haya estado que guardar entre los
dos pasos. El `submit` **no** vuelve a pedir prueba de wallet, y no hace falta:
lo que se envía es una transacción firmada por el principal, y el contrato la
rechaza si no lo es. Pedir una segunda prueba agregaría un paso sin agregar una
garantía.

## 4. La página, verificada en el navegador

```
$ curl -o /dev/null -w "HTTP %{http_code}" http://localhost:8899/revocar/mnd_…NOPE01
HTTP 200

$ curl http://localhost:8899/api/revoke/mnd_…NOPE01
{"ok":false,"code":"MandateNotFound","message":"no existe ese permiso",…}
HTTP 404
```

Abierta en el navegador con un id inexistente, la página renderiza y muestra
"no existe ese permiso" en su estado de error. (El 404 que aparece en la
consola es esa misma llamada — es el caso bajo prueba, no un defecto.)

`revocar.html` reusa el mismo lenguaje visual que `consent.html`: se extrajo su
bloque de estilos en vez de escribir uno nuevo, así las dos páginas que una
persona ve en el dominio de AgentPey se ven como el mismo sitio.

## 5. El link desde RealOps, y su honestidad

La pantalla del agente firmado ahora lleva:

> **Revocar este permiso**
>
> Revocar corta la autorización **desde afuera del agente**: no importa qué le
> digan después, sin Mandato válido no puede pagar nada. Se hace en el sitio de
> AgentPey y lo firmás con tu wallet — RealOps no puede revocar por vos, ni
> aunque quisiera.

Con prueba:

```
✓ links to AgentPey's revocation page, and is honest that it cannot revoke
```

El `?volver=` de la vuelta **solo acepta una ruta relativa**. Una URL absoluta
desde el query string sería exactamente la redirección abierta que `C-95`
existe para prevenir, y esta página no la reintroduce por la puerta de atrás.
