## 5. El vault lee los totales de un caché en memoria

`packages/vault/src/postgres-vault.ts`, al construirse:

```ts
({ rows } = await pool.query<VaultRow>(
  "select seq, prev_hash, hash, entry from vault_records where tenant_id = $1 order by seq asc",
  [tenantId],
));
```

y después:

```ts
async spentOn(subject, currency, at) {
  const total = totals.get(subject)?.get(currency)?.get(utcDayKey(at)) ?? 0n;
  return unscaleAmount(total);
}
```

`totals` se calcula una vez, sobre las filas leídas al construir, y se
actualiza solo con lo que **este** proceso escribe. Un segundo proceso ve un
`spentToday` desactualizado.

Quién consume ese valor — `apps/agent/src/policy/policy-rail.ts`:

```ts
const spentToday = await ledger.spentOn(subject, currency, at);
```

Comparado contra `scope.limits.perDay` y contra
`mandate.credentialSubject.grant.limits.perDay`. Es decir: con dos procesos,
el `perDay` del camino de cuenta clásica es evadible. El camino `policy_rail`
no lo es, porque el contrato vuelve a aplicarlo on-chain.

El comentario del propio archivo ya acota el alcance de la mitigación
existente, que cubre escrituras y no lecturas:

> Same limit as the file backend (V-7): durable within one process writing
> this tenant's rows, not across more than one process at a time.

## 8. La sesión no es durable

`apps/web/src/server.ts`:

```ts
const sessions = new Map<string, DemoSession>();
```

`startSession()` emite una credencial (`agentpass.issue`) y ancla un Mandato
en **cada** llamada. Un reinicio del proceso borra el `Map`, y el siguiente
"Iniciar sesión" emite documentos nuevos en vez de recuperar los vigentes.
Es la brecha `G7`, y choca de frente con dos requisitos del objetivo:
renovar un mandato no debe crear un agente nuevo, y una sesión no debe crear
identidad nueva.
