### Los tres criterios de aceptación

```
✓ round-trips: a signed credential verifies and comes back intact
✓ rejects a raised spending limit with InvalidSignature
✓ an expired credential raises CredentialExpired, not InvalidSignature
```

El tercero afirma explícitamente ambas cosas: que el código es `CredentialExpired`
**y** que no es `InvalidSignature`.

**Nota sobre la segunda.** Solo un test la caza: el que verifica explícitamente
el alfabeto (`no +, / ni =`). Node y `jose` decodifican base64 de forma
tolerante, así que la criptografía sigue funcionando y todo lo demás pasa. Ese
test es la única defensa contra un bug que rompería la interoperabilidad con un
verificador JOSE estricto de terceros. **No lo borres.**

Es determinista, no probabilístico: una llave de 32 bytes en base64 estándar
**siempre** termina en `=`.

## Un flake encontrado y corregido

El test "mutated signature segment" cambiaba el último carácter base64url de la
firma. Falló en una corrida y pasó en las anteriores. Diagnóstico:

```
últimos caracteres posibles en una firma de 64 bytes: A Q g w
bytes(…A) === bytes(…B): true
```

Una firma Ed25519 son 64 bytes = 512 bits; 86 caracteres base64url son 516 bits.
El último carácter lleva solo **2 bits significativos** y 4 de relleno, así que
`…A` y `…B` decodifican a bytes idénticos. La mutación era un no-op cuando el
último carácter era `A` — aproximadamente el 25% de las corridas.

Corregido mutando los bytes decodificados, no el texto. Ocho corridas
consecutivas después:

```

```
