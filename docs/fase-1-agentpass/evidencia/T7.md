El primer test es exactamente la secuencia pedida:

1. `issue()` → JWS de tres segmentos, hash de 64 hex, hash de transacción no vacío
2. `status(hash)` → `"Active"`
3. `verify(jws)` → los tres chequeos pasan; `issuerAddress` coincide con el emisor
4. `revoke({ hash, issuer })`
5. `status(hash)` → `"Revoked"`
6. `verify(jws)` con **el mismo JWS byte a byte** → falla con `CredentialRevoked`

Cada corrida genera una credencial nueva (nonce en `agent.name`), así que el hash
es distinto cada vez y el test es repetible. Segunda corrida: 3/3 en 14,7s.

## Dos suposiciones mías que la red desmintió

**1. `status` no devuelve un string.** El CLI de Stellar imprime `"Active"`, así
que asumí que el SDK haría lo mismo. Devuelve un objeto etiquetado:

```
status ctor: Object | JSON: {"tag":"Unknown"}
```

El test falló con `the registry returned an unknown status` y
`details.status: "[object Object]"`. La validación con zod convirtió lo que
habría sido un error silencioso en uno inmediato y legible.

**2. Una escritura necesita cuenta de origen.** El cliente se creaba sin llave
pública, lo cual funciona para lecturas (simulan desde una cuenta nula) pero no
para escrituras:

```
Error: This transaction was constructed using a default account.
Provide a valid publicKey in the AssembledTransactionOptions.
```

Ahora `anchor`, `revoke` y las operaciones de admin pasan la llave pública del
firmante en cada llamada.

Es la segunda vez que suponer la forma de este borde cuesta un fallo — la
primera fue `get_admin` en T6. Por eso el borde sin tipos está confinado a
`registry.ts` y todo lo que lo cruza pasa por zod.
