tras generar esto). El registro simulado sigue las mismas reglas que el

**Qué muestra cada bloque.**

- **1:** el contrato mismo rechaza anclar sin que el principal esté registrado
  como emisor — no es un chequeo que `@agentpay/mandate` agregó, es
  `agent_registry`'s propia regla, la misma que ya rige a un emisor de
  credenciales.
- **2–3:** anclado. `getCredential` (equivalente de prueba a `get_credential`
  del contrato) confirma el mapeo de `M-3` sin invertir: el `subject` guardado
  es el **agente**, el `issuer` es el **principal** — no al revés.
- **4:** las cuatro verificaciones pasan: firma, ventana firmada, estado
  anclado, principal todavía confiable.
- **5–6:** el principal revoca desde afuera. El mismo JWS, la misma firma
  válida, deja de verificar — con **su propio código** (`MandateRevoked`, no
  `CredentialRevoked`).
- **7:** un mandato individualmente activo deja de verificar si el registro
  **desactiva al principal** (`deactivate_issuer`, la misma operación de admin
  que ya existía) — el kill-switch global del registro alcanza también a los
  mandatos, no solo a las credenciales.

## 4. Mutation testing

Nueve mutaciones deliberadas sobre `anchor.ts`. **Ocho cayeron.**

```
killed    M1 anchor: registry mismatch never checked
killed    M2 verify: registry mismatch never checked
killed    M3 verify: Revoked treated as Active
killed    M4 verify: Unknown treated as Active
SURVIVED  M5 verify: principal registration never checked
killed    M6 verify: principal active flag never checked
killed    M7 anchor: subject is the principal, not the agent
killed    M8 anchor: expiresAt taken from validFrom
killed    M9 verify: principalAddress derived from the agent, not the principal
```

**Dos de estas se investigaron a fondo, como en cada hito anterior.**

- **M7** (anclar con el `subject` invertido — el principal en vez del agente)
  sobrevivió en la primera pasada porque el registro simulado ni siquiera
  guardaba el campo `subject`. Era un hueco real: nada podía haber detectado
  el error más importante que `M-3` existe para prevenir — invertir a quién
  empodera el mandato. Se agregó `getCredential()` al registro simulado
  (equivalente de prueba al `get_credential()` real del contrato) y el test
  que compara lo anclado contra el mapeo exacto de `M-3`. Con eso, cae.
- **M5** (quitar el chequeo de "¿el principal está registrado?" dentro de
  `verify`) **sigue sobreviviendo, y es equivalente, no un hueco.** El
  contrato no tiene ninguna operación de "des-registrar" un emisor — solo
  `register_issuer` y `deactivate_issuer` (que sí se testea, y sí cae en M6).
  Una vez que `anchor()` exige el registro para crear el registro on-chain, no
  existe ningún camino real por el que `verify()` encuentre después un
  principal *nunca* registrado — solo uno desactivado. El mismo patrón ya
  existe, sin testear, en `AgentPass.verify()` de la Fase 1
  (`packages/sdk/src/index.ts`, chequeo de `IssuerNotRegistered`): no es algo
  que este hito introdujo, es simetría defensiva con el chequeo de
  `IssuerInactive` que sí es alcanzable.
