Lo que hay que mirar en esa salida:

1. **Activa:** cuatro herramientas. `create_purchase_intent` está y falla con
   `NotImplemented` — su comportamiento es de T12/T13, pero *existe*.
2. **Revocada:** tres herramientas. `create_purchase_intent` no aparece en la
   lista, y llamarla da **`UnknownTool`**, no un permiso denegado. Nadie le dijo
   al agente que no puede: no hay nada que llamar.
3. **Vencida:** idéntico, con `CredentialExpired` como causa. Mismo documento,
   mismo hash — solo cambió el reloj.
4. **Firma falsificada:** el reporte trae el código del fallo y el hash, y
   **nada del contenido del documento**. No aparece `compras-demo`, ni el
   `perTx`, ni el operador. Si la firma no verifica, todo lo que dice adentro lo
   eligió quien lo falsificó, y repetirlo sería presentar una falsificación como
   dato. El hash sobrevive porque se calcula sobre los bytes recibidos, no se lee
   de adentro.

En los cuatro casos `list_products` sigue funcionando: lo que se le quitó al
agente es la autorización de compra, no el agente entero.

## Cómo se prueba sin red sin que la prueba pierda valor

El doble de test corre **de verdad** los dos chequeos offline —firma Ed25519 y
ventana de vigencia, con `signCredential` y `verifyCredential` de
`@agentpass/core`, sobre llaves Stellar reales— y simula **solo** el tercero, la
consulta al registro, que es el único que necesita red.

Un doble que también falsificara la firma no probaría nada: el test de la
firma falsificada de arriba pasa porque la verificación criptográfica es
auténtica.

## El puerto es angosto a propósito

El agente recibe un `CredentialVerifier` con **un solo método**, no el SDK
completo. No es una convención: es que el agente estructuralmente no puede
emitir una credencial, no puede revocar una y no puede registrar un emisor.

```ts
export interface CredentialVerifier {
  verify(jws: string, options?: { readonly now?: Date }): Promise<VerifiedOwnCredential>;
}
```

Que el SDK real encaje sin adaptador se comprueba **en tiempo de compilación**,
no en runtime — si `verify` cambiara de forma en `@agentpass/sdk`, esto deja de
compilar:

```ts
it("AgentPass from the SDK satisfies CredentialVerifier", () => {
  const conforms = (agentPass: AgentPass): CredentialVerifier => agentPass;
  expect(typeof conforms).toBe("function");
});
```

M11 mereció dos intentos. El primero fue una mutación mal escrita que no

verdad ocurriría: alguien agrega el contenido del documento al estado inusable
*para dar mejor diagnóstico*. Escrita así, cae sola. Vale la distinción: una
mutación que no cambia el comportamiento no es evidencia de que el test sirva.

## Fail-closed también cuando no se sabe

Un timeout del RPC deja el estado on-chain **desconocido**, y un agente que no
puede confirmar su autorización no debe actuar sobre ella — la misma dirección
de `B-1`. La causa igual sobrevive en `problem.code`, así que una caída de red
sigue siendo distinguible de una revocación:

```
NetworkError  -> herramienta retirada, causa "the credential could not be checked"
CredentialRevoked -> herramienta retirada, causa "the registry reports this credential as revoked"
```
