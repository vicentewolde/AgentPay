Las tres cosas que hay que mirar:

1. **Los dos productos con prompt injection son rechazados por monto**, igual que
   `set-copas-vidrio-soplado`, que pide lo mismo con una descripción
   perfectamente normal. El texto no cambió el resultado en ninguna dirección.
2. **El mismo producto inyectado, a cantidad 2, pasa.** La inyección no es el
   motivo del rechazo — el monto lo es. Si el rechazo viniera de "el agente
   detectó texto hostil", este caso también caería.
3. **La última tabla es la prueba en su forma más directa:** el mismo producto,
   el mismo precio, la misma cantidad, cuatro descripciones radicalmente
   distintas — desde la original hasta una vacía, pasando por dos inyecciones —
   y la decisión sale idéntica, con el mismo total al último decimal.

## Por qué el texto no puede influir: no es un argumento, es la firma

```ts
export interface ScopeRequest {
  readonly venue: string;
  readonly asset: string;
  readonly unitAmount: string;
  readonly quantity: number;
}

export function checkScope(scope: Scope, request: ScopeRequest): ScopeDecision;
```

`checkScope` **nunca recibe un producto.** No hay un campo por el que la prosa
del comercio pueda viajar hasta la decisión. No es "el agente tiene instrucciones
de ignorarla" ni "el texto se filtra antes": el texto no es una entrada.

## Los 26 tests de inyección

`src/injection.test.ts` prueba nueve estilos de ataque —imperativo, haciéndose
pasar por un system prompt, alegando consentimiento fuera de banda, declarando un
alcance falso, simulando el resultado de una herramienta, urgencia, ingeniería
social cortés, confusables Unicode, y una carga de 1.800 caracteres— en **las dos
direcciones**:

- **Agregar** la inyección a un producto limpio: la decisión es idéntica byte a
  byte a la del producto sin tocar.
- **Quitar** la inyección de un producto hostil: sigue rechazado, con el mismo
  código y el mismo total.

La segunda dirección es la que más importa. Si el rechazo viniera de que el
agente notó texto hostil, quitar el texto dejaría pasar la compra.

También cubre la inyección en el **nombre** del producto, no solo en la
descripción, y el caso combinado: credencial revocada + producto inyectado →
`UnknownTool`, porque no hay herramienta que persuadir.

### El hallazgo de M13

La primera versión de M13 **no rompió ningún test**. La causa no fue una
protección faltante sino una mutación mal escrita: `Math.round(Number(x) * q *
1e7)` borra el error de punto flotante para todos los valores que los tests
usaban, así que la mutación **no cambiaba el comportamiento**. Es exactamente el
mismo tipo de hallazgo que M1 en T9: una mutación que no cambia nada no prueba
nada sobre el test.

Pero al analizarla apareció un hueco real: `scope.test.ts` no verificaba la
aritmética en el borde, solo delegaba en los tests de `amount.ts`. Si alguien
cambiara la implementación **dentro** de `checkScope`, esos tests seguirían en
verde. Se agregaron cinco casos al nivel de la decisión, cada uno con un producto
cuyo resultado en punto flotante se pasa del límite:

```ts
it.each([
  ["0.1 x 3 against 0.3",       "0.1",   3, "0.3",   0.1 * 3],
  ["0.07 x 3 against 0.21",     "0.07",  3, "0.21",  0.07 * 3],
  ["1.1 x 3 against 3.3",       "1.1",   3, "3.3",   1.1 * 3],
  ["0.035 x 3 against 0.105",   "0.035", 3, "0.105", 0.035 * 3],
])("allows %s", (_label, unitAmount, quantity, perTx, floatProduct) => {
  // La premisa: en punto flotante este producto realmente se pasa del limite.
  expect(floatProduct).toBeGreaterThan(Number(perTx));
  expect(decide({ limits: { perTx, ... } }, { unitAmount, quantity }).allowed).toBe(true);
});
```

El `expect(floatProduct).toBeGreaterThan(...)` es deliberado: afirma la premisa
del test dentro del test, así que si algún día `0.1 * 3` dejara de desbordarse,
el test avisa en vez de volverse silenciosamente trivial. Dos de los cuatro casos
que había elegido primero (`22.00 x 10` y `0.0000003 x 3`) resultaron ser exactos
en punto flotante y esa aserción los cazó de inmediato.

Con esos tests, ambas formas realistas de la mutación caen — incluida `M13c`, la
que antes sobrevivía.

## `perDay` no se aplica, a propósito

Un total diario necesita memoria de gastos pasados: eso es *enforcement*, no un
chequeo de alcance, y es de PolicyRail en la Fase 3. Hay un test que fija la
frontera — una compra dentro de `perTx` pasa aunque supere ampliamente `perDay`:

```ts
it("a purchase within perTx passes even when it dwarfs perDay", () => {
  expect(decide({ limits: { perTx: "50.00", perDay: "0.01", currency: "USDC" } },
                { unitAmount: "50.00" }).allowed).toBe(true);
});
```

Sin ese test, media implementación de `perDay` podría entrar sin que nada avise.
